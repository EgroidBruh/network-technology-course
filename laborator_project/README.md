# Сервис дежурств: набросок API

Простое FastAPI-приложение по первым трём сценариям из DOCX: создание сотрудника, определение текущего дежурного и регистрация инцидента. Пока без БД, ORM, авторизации и отдельных микросервисов. Данные хранятся в памяти одного процесса и очищаются при перезапуске. Запускайте один worker.

## Структура

```text
main.py                      # Создание приложения, подключение роутеров, временные данные
models/
├── __init__.py
├── create_employee.py       # Модели сценария 1
├── current_duty.py          # Модели сценария 2
└── register_incident.py     # Модели сценария 3 и IncidentCreatedEvent
routes/
├── __init__.py
├── create_employee.py       # Сценарий 1: создание сотрудника
├── current_duty.py          # Сценарий 2: определение дежурного
└── register_incident.py     # Сценарий 3: регистрация инцидента
tests/test_incidents.py      # Проверки регистрации и ошибок входных данных
Dockerfile
compose.yaml
requirements.txt
```

Бизнес-логика пока находится рядом с endpoints. Когда появится постоянное хранение, её можно вынести в слой сервисов, добавить репозитории с SQLAlchemy и разделить приложение на микросервисы. В `models/` находятся только Pydantic-схемы API, разделённые по сценариям.

## Запуск

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m uvicorn main:app --reload
```

Или в Docker:

```bash
docker compose up --build
```

Swagger UI: http://localhost:8000/docs. Вся работа с наброском доступна через него.

## Endpoints

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/employees` | Создать сотрудника |
| GET | `/employees` | Посмотреть созданных сотрудников |
| GET | `/employees/{employee_id}` | Получить сотрудника |
| POST | `/duty/shifts` | Добавить смену для проверки сценария 2 |
| GET | `/duty/shifts` | Посмотреть смены |
| PUT | `/duty/default` | Назначить резервного старшего смены |
| GET | `/duty/current` | Получить текущего или резервного дежурного |
| POST | `/incidents` | Принять событие мониторинга и зарегистрировать инцидент |
| GET | `/incidents` | Посмотреть зарегистрированные инциденты |
| GET | `/incidents/{incident_id}` | Получить карточку инцидента |
| GET | `/incidents/{incident_id}/events` | Посмотреть сформированное событие IncidentCreatedEvent |

## Как попробовать

1. Создайте сотрудника через `POST /employees`:

```json
{
  "first_name": "Иван",
  "last_name": "Иванов",
  "email": "ivan@example.com",
  "position": "Системный администратор",
  "role": "SHIFT_LEAD",
  "work_phone": "+73470000001",
  "mobile_phone": "+79000000001"
}
```

Сохраните `id` из ответа. Отчество (`middle_name`) необязательно. Роли: `SPECIALIST`, `SHIFT_LEAD`, `MANAGER`, `ADMIN`. Телефоны задаются с `+` и 8–15 цифрами, без пробелов. Повторный email или телефон возвращает `409`; ошибочные поля — `422`.

2. Добавьте смену через `POST /duty/shifts`, подставив UUID сотрудника и актуальные даты:

```json
{
  "employee_id": "UUID сотрудника",
  "start_time": "2026-10-19T08:00:00+05:00",
  "end_time": "2026-10-19T20:00:00+05:00"
}
```

Часовой пояс обязателен. Конец должен быть позже начала; пересечения смен запрещены (`409`). По условию DOCX обе границы включены: `start_time <= now <= end_time`.

3. Вызовите `GET /duty/current`. Ответ содержит UUID, ФИО, мобильный телефон, источник назначения (`schedule` или `default`) и момент определения.

Для резервного назначения выполните `PUT /duty/default`:

```json
{"employee_id": "UUID сотрудника с ролью SHIFT_LEAD"}
```

Когда текущая смена отсутствует, возвращается резервный сотрудник и пишется предупреждение в лог. Если оба не назначены, возвращается `503`. Реальная доставка тревог администратору и телефония пока не подключены. Текущее время берётся с сервера приложения.

## Сценарий 3: регистрация инцидента

Отправьте REST/Webhook-запрос `POST /incidents`:

```json
{
  "source": "Zabbix",
  "error_code": "HTTP_503",
  "title": "Сервис недоступен",
  "description": "Сервер api-01 отвечает HTTP 503",
  "severity": "CRITICAL"
}
```

Все поля обязательны. `source` — название источника, `error_code` — строковый код ошибки, `title` — краткий заголовок карточки. Допустимые уровни критичности: `INFO`, `WARNING`, `CRITICAL`. Пустые строки и неизвестные поля отклоняются.

При корректном запросе возвращается `201`: переданные данные, UUID инцидента, `status: "OPEN"` и время регистрации `created_at` в UTC. Одновременно создаётся `IncidentCreatedEvent` с собственным UUID, ID инцидента, критичностью и временем события. Его можно посмотреть через `GET /incidents/{incident_id}/events`.

При некорректных данных возвращается `422`; ни инцидент, ни событие не сохраняются. Неизвестный UUID инцидента возвращает `404`. Каждый корректный POST регистрирует новый инцидент; дедупликации пока нет.

Событие только сохраняется в памяти приложения. Alertmanager, брокер сообщений, запуск обзвона и обработчик оповещений не подключены. Endpoint принимает наш JSON-контракт; прямого адаптера штатных webhook-форматов Zabbix, Prometheus или Alertmanager пока нет.

## Проверка

```bash
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q
```

Проверяются регистрация инцидента и события, ошибки валидации без сохранения данных, уровни критичности, неизвестные UUID и доступность прежних роутеров.

Это набросок для локальной проверки endpoints: общей памяти между процессами и защиты от одновременных изменений нет. БД и микросервисы добавятся позже.
